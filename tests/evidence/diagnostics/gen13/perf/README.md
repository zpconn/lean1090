# Gen13 native sampling evidence

This is one native `perf record -e cpu-clock:u -F 199 --call-graph dwarf,16384` pass over the complete corpus through the frozen headline worker, pinned to guest logical CPU 0. It is diagnostic sampling, not an ABAB benchmark or a throughput measurement. The worker's raw response shows protocol completion; its instrumented duration is not a performance result.

The capture runs the actual gen13 timed binary, SHA-256 `b13fac61e8bd1170cdcacae3c3c054bc05f484da39ebf2d823dd868ab5920730`, from commit `247a28d9a681fd5fac37a630cc4a889e30000490`. The helper verifies all 22 linked source/C/object/trace sets against `bench/runs/gen13/fresh-native-inputs.json`, every linked source against its committed blob, and all native hashes against `binary-built.json`. All 140 captured source/native/provenance hashes match before and after, including the held proof sources. The diagnostic driver build finished before this pass; root readiness and its exact driver-build hash are bound in `capture.json`. Native diagnostic and Callgrind jobs were held until capture completion. Other agents could read evidence or prepare orchestration; this does not establish Windows host-wide isolation.

`run_perf_gen13.py` and `analyze_perf_gen13.py` adapt the retained gen9/gen10 helpers, retaining exact current-commit checks because this timed commit already uses the current attribution. The capture command, inputs, affinity, preserved binary path and raw-data hash are in `capture.json`. The preserved binary copy is for later symbol lookup and was not executed. Raw perf data remains `.cache/gen13-costs/perf-gen13/perf.data`; the campaign archiver retains it via its explicit `--perf-data` option. The helper does not rebuild production code or alter its native image. The shared syndrome computation introduced in gen6 remains directly beneath `Impl.decode`; the analyzer labels that visible path separately instead of charging it to report construction.

All 267 recorded samples parse. Explicit loss counters: report-self.txt line 4: `# Total Lost Samples: 0`; report-children.txt line 4: `# Total Lost Samples: 0`. Exactly 61 samples have the live `Impl.decode` frame; 206 others are excluded and separately classified. Unknown frames occur in 259 recorded stacks and 0 included leaf positions. Missing, inlined or tail-called frames may bias the visible subset; absence of the decoder frame does not prove a sample is preparation. The unresolved report substage remains explicit. Disjoint tables sum to 61; nested Rat/GMP/Parity/software-binary64/enclosure categories overlap and must not be added together. Absence of an inlined lookup helper frame does not establish zero lookup cost.

The runtime eagerly initializes its 13 immutable field-density tables, 1,024-entry Mach-value table, 4,096-entry QNH-value table and 2,047-entry BDS50 wind-penalty table during module startup before `main`. These initialization costs are outside the decode-visible subset when their actual stacks lack `Impl.decode`; they are not assigned to a decoder stage by assumption. The recording also contains input preparation, result consumption/destruction, runtime startup and possible unwind failures. Conditional shares among visible decoder stacks are not whole-decoder timing shares or proof of causal speedup. The current generated C uses a `uint32_t` accumulator in the tail-loop compiled from `Nat.fold`, with the existing cached-bit/fallback logic. Its inlined step can disappear from stacks, so missing step frames do not imply zero CRC work. The gen12 byte path additionally inlines bounded UInt64 byte folds into `bytesValue`, retaining the live prefix helper and original Nat fallback for inputs longer than sixteen bytes. Changed ownership and tail-call conventions may alter visible stage frames; conditional counts do not establish comparable whole-stage timing. Gen13 adds a callable BDS50 wind helper with two missing-status exits and one table load on its present path; all three software rounds occur in the persistent table initializer, not this lookup. Its initialization cost is still recorded outside the decode-visible subset. The benchmark and exhaustive Callgrind accounting are separate evidence.
