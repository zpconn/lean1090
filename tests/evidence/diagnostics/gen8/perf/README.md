# Gen8 native sampling evidence

This is one native `perf record -e cpu-clock:u -F 199 --call-graph dwarf,16384` pass over the complete corpus through the frozen headline worker, pinned to guest logical CPU 0. It is diagnostic sampling, not an ABAB benchmark or a throughput measurement. The worker's raw response shows protocol completion; its instrumented duration is not a performance result.

The capture runs the actual gen8 timed binary, SHA-256 `da5ebfa685b052a3b534001fc2a1d4ead02995e40f2ea077e6f8d6328b4dde31`, from commit `78286f12feb79f8d8e3cdf2411ebd274161d1c3d`. The helper verifies all 22 linked source/C/object/trace sets against `bench/runs/gen8/fresh-native-inputs.json`, every linked source against its committed blob, and all native hashes against `binary-built.json`. All 135 captured source/native/provenance hashes match before and after, including the held proof sources. The diagnostic driver build finished before this pass; root readiness and its exact driver-build hash are bound in `capture.json`. Native diagnostic and Callgrind jobs were held until capture completion. Other agents could read evidence or prepare orchestration; this does not establish Windows host-wide isolation.

`run_perf_gen8.py` and `analyze_perf_gen8.py` adapt the retained gen7 helpers. The capture command, inputs, affinity, preserved binary path and raw-data hash are in `capture.json`. The preserved binary copy is for later symbol lookup and was not executed. Raw perf data remains `.cache/gen9-planning/perf-gen8/perf.data`; the campaign archiver retains it via its explicit `--perf-data` option. The helper does not rebuild production code or alter its native image. The shared syndrome computation introduced in gen6 remains directly beneath `Impl.decode`; the analyzer labels that visible path separately instead of charging it to report construction.

All 323 recorded samples parse. Explicit loss counters: report-self.txt line 4: `# Total Lost Samples: 0`; report-children.txt line 4: `# Total Lost Samples: 0`. Exactly 160 samples have the live `Impl.decode` frame; 163 others are excluded and separately classified. Unknown frames occur in 320 recorded stacks and 19 included leaf positions. Missing, inlined or tail-called frames may bias the visible subset; absence of the decoder frame does not prove a sample is preparation. The unresolved report substage remains explicit. Disjoint tables sum to 160; nested Rat/GMP/Parity/software-binary64/enclosure categories overlap and must not be added together. Absence of an inlined lookup helper frame does not establish zero lookup cost.

The runtime eagerly initializes its 13 immutable field-density tables and 1,024-entry Mach-value table during module startup before `main`. These initialization costs are outside the decode-visible subset when their actual stacks lack `Impl.decode`; they are not assigned to a decoder stage by assumption. The recording also contains input preparation, result consumption/destruction, runtime startup and possible unwind failures. Conditional shares among visible decoder stacks are not whole-decoder timing shares or proof of causal speedup. The benchmark and exhaustive Callgrind accounting are separate evidence.
