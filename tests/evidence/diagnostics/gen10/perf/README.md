# Gen10 native sampling evidence

This is one native `perf record -e cpu-clock:u -F 199 --call-graph dwarf,16384` pass over the complete corpus through the frozen headline worker, pinned to guest logical CPU 0. It is diagnostic sampling, not an ABAB benchmark or a throughput measurement. The worker's raw response shows protocol completion; its instrumented duration is not a performance result.

The capture runs the actual gen10 timed binary, SHA-256 `e2b7efcfa6aa3a3f2e234aa97d95fabc59a4a8c15562b098f20f1f0ab4f95586`, originally timed at commit `d51a3040984beb6f0f96b0f4fcf225ba2622a7e0`. The attribution-only rewrite maps that commit to `0131adfd5fe6f2ba4b18af1b7f8dccdb474354a5` with the identical Git tree. Current HEAD is `95bc97d75d83190371768950e56ef7cc0825308d`; every linked source is checked against all three commits. Original records are preserved unchanged and the mapping's raw Git commit metadata and object IDs are verified. The helper verifies all 22 linked source/C/object/trace sets against `bench/runs/gen10/fresh-native-inputs.json`, every linked source against its committed blob, and all native hashes against `binary-built.json`. All 139 captured source/native/provenance hashes match before and after, including the held proof sources. The diagnostic driver build finished before this pass; root readiness and its exact driver-build hash are bound in `capture.json`. Native diagnostic and Callgrind jobs were held until capture completion. Other agents could read evidence or prepare orchestration; this does not establish Windows host-wide isolation.

`run_perf_gen10.py` and `analyze_perf_gen10.py` adapt the retained gen9 helpers. The capture command, inputs, affinity, preserved binary path and raw-data hash are in `capture.json`. The preserved binary copy is for later symbol lookup and was not executed. Raw perf data remains `.cache/gen10-costs/perf-gen10/perf.data`; the campaign archiver retains it via its explicit `--perf-data` option. The helper does not rebuild production code or alter its native image. The shared syndrome computation introduced in gen6 remains directly beneath `Impl.decode`; the analyzer labels that visible path separately instead of charging it to report construction.

All 301 recorded samples parse. Explicit loss counters: report-self.txt line 4: `# Total Lost Samples: 0`; report-children.txt line 4: `# Total Lost Samples: 0`. Exactly 93 samples have the live `Impl.decode` frame; 208 others are excluded and separately classified. Unknown frames occur in 289 recorded stacks and 0 included leaf positions. Missing, inlined or tail-called frames may bias the visible subset; absence of the decoder frame does not prove a sample is preparation. The unresolved report substage remains explicit. Disjoint tables sum to 93; nested Rat/GMP/Parity/software-binary64/enclosure categories overlap and must not be added together. Absence of an inlined lookup helper frame does not establish zero lookup cost.

The runtime eagerly initializes its 13 immutable field-density tables 1,024-entry Mach-value table and 4,096-entry QNH-value table during module startup before `main`. These initialization costs are outside the decode-visible subset when their actual stacks lack `Impl.decode`; they are not assigned to a decoder stage by assumption. The recording also contains input preparation, result consumption/destruction, runtime startup and possible unwind failures. Conditional shares among visible decoder stacks are not whole-decoder timing shares or proof of causal speedup. The benchmark and exhaustive Callgrind accounting are separate evidence.
